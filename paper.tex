\title{Learning Simple Preventive Actions Against Cascading Failures:\\
A Reproducible IEEE 118-Bus Study}

\author{\IEEEauthorblockN{Saksham Mishra}
\IEEEauthorblockA{\textit{Department of Computer Science}\\
University of Birmingham Dubai, UAE}}

\maketitle

\begin{abstract}
A cascading failure is a chain reaction: one overloaded line trips, neighbouring lines pick up the extra flow, and a local problem can become a blackout. This short paper asks a practical question that a second-year computer-science student can explain: if we let a small learning agent make \emph{one} gentle move \emph{before} the accident (nudge storage, reactive power, renewables, or demand), does the cascade happen less often than if we do nothing? We build a fully open testbed on the IEEE 118-bus network, inject 1{,}000 weather-driven wind and solar profiles, and compare four options on the same 150 held-out scenarios: do nothing, a simple if-then rule, a slow optimal-power-flow (OPF) solver, and a Deep Deterministic Policy Gradient (DDPG) agent. On this test the cascade rate falls from 34.0\% (do nothing) to about 30\% for both the rule and DDPG. DDPG is about $1.9\times$ faster than OPF (299~ms vs.\ 568~ms per decision). The gain is modest and not statistically significant at this sample size. The contribution is therefore a \emph{reproducible, honest} student-scale study: weather, grid, agent, and evaluation scripts are in one repository, with fixed random seeds so another group can rerun the same accidents.
\end{abstract}

cascading failure, reinforcement learning, DDPG, IEEE 118-bus, preventive control, reproducibility

\section{Introduction}

Power grids fail in a way that is easy to picture. Think of a busy road network. If one motorway lane closes, cars spill onto the next road. If that road is already full, it jams too. In a grid the ``roads'' are transmission lines and the ``cars'' are electrical power. When a line trips, power reroutes. If another line then exceeds its thermal limit, it also trips. That chain is a \emph{cascade}.

Today most tools still \emph{react} after something has already gone wrong. We study a simpler idea: take a small preventive action while the grid is still intact, then see whether the later cascade is milder. The action has to be explainable. Our agent is only allowed four knobs, each with a tight limit so it cannot ``fix'' the grid by shedding huge amounts of load:

\begin{itemize}
\item charge or discharge a modest storage unit ($\pm$15~MW);
\item add or absorb a little reactive power ($\pm$10~MVAr);
\item curtail some wind/solar (up to 20\%);
\item reduce demand a little (up to 15\%).
\end{itemize}

That is the whole control story. No topology switching, no secret extra actuators.

\paragraph{What is new here?}
Not a claim that deep learning ``solves blackouts''. Three things are useful and new enough for a short paper: (1)~a weather-stressed IEEE 118-bus playground that anyone can regenerate from a config file; (2)~a \emph{fair} test in which every method faces the \emph{same} sampled accident on each scenario; (3)~an honest comparison in which a tiny learning agent, a handwritten rule, and a classical optimiser are scored with the same physics simulator.

\paragraph{What this is not.}
This is a laboratory prototype on a standard test network, not a live utility deployment. In technology-readiness language it sits around a working simulation with a closed-loop agent (roughly TRL~4), not a fielded product.

\section{The Story in One Picture}

The pipeline has four stages, all in the public GitHub repository.

\begin{enumerate}
\item \textbf{Grid.} Load the IEEE 118-bus case (118 buses, 173 lines, 54 generators) and scale demand to 180\% of the textbook loading so the system is stressed enough that cascades can actually occur.
\item \textbf{Weather.} Sample 1{,}000 day-long wind and solar traces (seed 42). Wind uses a standard turbine curve; solar follows a day/night pattern with random cloudiness. Ten buses host wind, eight host solar.
\item \textbf{Learning.} A DDPG agent sees a snapshot of the grid (voltages, line loadings, generator output, a short weather look-ahead, and time of day: 489 numbers) and outputs the four knobs above. During training we do \emph{not} run the expensive cascade. We only reward a healthy-looking grid: voltages near 1.0~pu, lines not packed, and small actions. That keeps training cheap on a laptop.
\item \textbf{Test.} For each of 150 unseen weather days, at peak hour (hour 12), every method takes at most one action. Then we run a physics cascade: sample an N-1/N-2/N-3 accident with a seed tied to the scenario index, trip those elements, and iterate overloads until the system settles or we hit a 15-step cap. The same accident is replayed for every method.
\end{enumerate}

\section{Methods (Plain Language)}

\subsection{How we decide that a cascade happened}

After the accident we measure how much customer demand had to be dropped to keep the remaining network solvable. If almost nothing is dropped, we call it a non-event. If a noticeable fraction is dropped, we call it a cascade. We also record the mean dropped demand across all 150 days (``load shed'').

\subsection{The four methods}

\textbf{Do nothing.} Apply weather, run the accident, no control. This is the baseline.

\textbf{If-then rule.} If any line is above 90\% loading, or any bus voltage leaves the 0.95--1.05~pu band, apply a fixed recipe (partial storage, reactive support, 20\% curtailment, 10\% demand cut). Otherwise sit still. A first-year student can recode this in a few lines.

\textbf{OPF.} Ask pandapower's optimal power flow to redispach generators under thermal and voltage limits, then run the same accident. This is the ``slow but physics-aware'' adult in the room. It is not a learning method.

\textbf{DDPG agent.} Actor--critic networks (489$\rightarrow$256$\rightarrow$128$\rightarrow$4). We train 100 short episodes, two random seeds, with and without prioritized replay. Full settings live in \texttt{config.yaml}. The agent is frozen at test time: one forward pass, one action, then the cascade simulator.

\subsection{Fairness rules}

\begin{itemize}
\item Train / validation / test split is 700 / 150 / 150, permutation seed 42.
\item Accident randomness for scenario $i$ uses seed $i+1000$, so method A and method B see the same trips.
\item We evaluate the \emph{full} test split (150 days), not a convenience subset of 25.
\end{itemize}

\paragraph{Reading the numbers without hype.}
Doing nothing cascades on 51 of 150 days (34\%). The if-then rule and DDPG both land near 30\%. That is about 5--6 extra ``saved'' days, not a transformed grid. A paired test on the rule versus do-nothing does not reach $p<0.05$ (McNemar $p\approx0.21$). So we report a \emph{small, consistent direction}, not a breakthrough.

\paragraph{Speed is the clean win versus OPF.}
OPF still helps a little (32\% cascade) but takes 568~ms on average. DDPG takes 299~ms---about $1.9\times$ faster---because a trained network does not re-solve an optimisation from scratch.

\paragraph{Rules are competitive.}
On this conservative action box, the handwritten rule slightly beats the mean DDPG seed on load shed (0.121 vs.\ 0.127). The better DDPG seed reached 29.3\% cascade and 0.119 shed (11 days prevented). A fair takeaway for a CS audience: \emph{if the knobs are this small, a good rule is a strong baseline, and learning is not automatically better}. That is a result, not a failure.

\section{How to Reproduce}

Clone \url{https://github.com/theSaksham02/Autonomous-grid-handling}. Python 3.10+, then:

\begin{verbatim}
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python run_pipeline.py --start 1 --end 5   # data
python run_stage6.py                       # train
python finish_stage6.py --n-test 150       # this paper's table
\end{verbatim}

All knobs (loading, weather seed, episode count, action limits) are in \texttt{config.yaml}. No paid cloud is required. Training and cascade tests are CPU-bound power-flow solves; a free Colab T4 is optional, not necessary.

\section{Limitations}

The action limits are intentionally tiny, so no method can perform miracles. The cascade model is a teaching-scale AC loop, not a vendor-grade dynamic simulator. We did not use real utility data. Statistical power at $n=150$ is limited. We did not claim live-grid TRL~6--7.

\section{Conclusion}

We asked whether a small, explainable learning agent can take one preventive step against weather-stressed cascades on IEEE 118-bus. Relative to doing nothing, both a simple rule and DDPG reduce cascade frequency from 34\% to about 30\% on 150 test days, and DDPG answers nearly twice as fast as OPF. The scientific value is a \emph{reproducible comparison}, not an inflated accuracy number. Future student work can widen the action box, lengthen the test set, or add a second corrective step after the first trip.
